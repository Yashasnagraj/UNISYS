>

We tap the bone with a precise vibration, record how it vibrates back, and use the resonance signature to compute exactly how stiff the bone is — and the AI tells the surgeon what day the patient is safe to walk."

## Live Q&A — what judges will ask and how to answer

**Q: "Where did your training data come from?"**

> "No public dataset of bone vibration signals exists — this is novel sensor work. So we generate training cases by running the same DSP pipeline that runs on the device, with biologically grounded noise added. This means zero distribution shift between training and inference. The methodology mirrors peer-reviewed structural health monitoring on bridges, composites, and cables — same physics, established technique."

**Q: "How do you defend 95 percent on synthetic data?"**

> "Three things. One: the *Delayed Union* boundary class is at 77 percent — that's the honest tell that the model is learning, not memorising. Two: we hold out a thousand unseen cases generated from a different random seed and the model still hits 95.6 percent. Three: every feature the AI uses is something a clinician can name in plain English. We can show you exactly why it made any specific prediction."

**Q: "Is this enough to clear a patient for walking?"**

> "For a research prototype demonstrating the principle, yes — and the technique is supported by 40 years of peer-reviewed literature. For an FDA-cleared device a surgeon could legally use to make weight-bearing decisions, no — we need clinical validation against IRB-approved gold standards, multi-axis sensing, and operator-position feedback. We've built the platform. The validation study is the next milestone. We know exactly where that line is."

**Q: "Why ESP32 and not STM32?"**

> "Three reasons. Cost — ESP32-S3 is five dollars versus twenty. WiFi and BLE on chip, no separate radio. And dual-core — we pin the SPI/DMA acquisition to core zero and the FFT to core one with hard isolation, so we never miss a sample. We use the `esp_dsp` library for the FFT."

**Q: "Why 20 to 200 Hz?"**

> "That covers the fundamental flexural mode of the human tibia — roughly 83 Hz unhealed to 101 Hz healed, per Cunningham 1990 and Nakatsuchi 1996. Higher modes exist but the fundamental is where the signal-to-noise is best and where the f-squared-equals-stiffness relationship is cleanest. The simulator goes up to 1.1 kHz for lab-grade analysis; the firmware narrow-bands to 20–200 Hz for field-portable use."

**Q: "What's the firmware actually doing?"**

> "Generates a 500-millisecond logarithmic chirp on the DAC. Reads the IIS3DWB accelerometer over SPI at 10 megahertz with DMA ping-pong. Runs a 1024-point radix-2 FFT on core one using the esp_dsp library. Locates the peak with sub-bin parabolic interpolation. Computes half-power bandwidth, damping ratio, Q-factor, TSI. All on-chip. The host gets a JSON line with the verdict plus the raw waveform."

**Q: "How would a hospital use this?"**

> "Day zero — surgeon scans the patient's healthy contralateral leg to set the personal baseline. After that, every follow-up visit is one scan on the injured leg, 20 seconds, no preparation. The device tells the surgeon: today's TSI, how that compares to the personal baseline, where on the healing curve this patient sits, and the projected safe-to-walk date. The doctor uses that to decide cast removal, physiotherapy progression, and weight-bearing clearance. The same data feeds the patient record over time."

## Code-walkthrough cheat sheet (only if asked to "show the code")

If a judge wants you to *show* code, open these in order and narrate one sentence each:

1. `ortho_simulator/engine/signal_generator.py` — "This is how the device-side chirp and the bone's resonance response are modelled. Damped harmonic oscillator, bilinear-transform IIR resonator."
2. `ortho_simulator/engine/fft_engine.py` — "Welch's method for PSD, parabolic peak interpolation, half-power bandwidth for the Q-factor. Same code logically runs on the ESP32 in C."
3. `ortho_simulator/engine/clinical_metrics.py` — "TSI = f-squared ratio. RUST is derived from TSI. Classification rules are the clinical decision logic, calibrated to the literature thresholds."
4. `ortho_simulator/ml/feature_extractor.py` — "The 25 features the AI sees. Spectral, time-domain, damping, clinical. Single source of truth shared by training and inference."
5. `ortho_simulator/ml/train_model.py` — "Five-fold stratified cross-validation, RandomForest versus GradientBoosting, hyperparameter grid, exports all the artifacts you see on the validation page."
6. `ortho_simulator/engine/healing_prediction.py` — "Personalised Gompertz fit per patient. Solves for the week the patient crosses TSI 80 percent. Edge cases handle non-union and already-cleared."
7. `firmware/main/fft_task.c` — "The on-device FFT pinned to ESP32 core 1. Same algorithm as `fft_engine.py` but in C, using `esp_dsp`."
